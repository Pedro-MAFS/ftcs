# US-MAIL-03 · 写新邮件、引用回复和保留草稿

0.6.4 · 已实现，待真实邮箱联测。本故事交付邮箱会话底部的撰写区，以及从点击「发送」到邮件出现在时间线的完整流程。沿用现有联系人列表、时间线、原邮件跳转和附件读取能力。参见[需求与验收条件](../43-需求-工作区邮箱与即时通讯式会话.md#us-mail-03--写新邮件引用回复和保留草稿)、[邮箱界面稿](工作区邮箱.pen)、[账号数据模型](工作区邮箱数据模型设计.md)。

## 1. 用户如何写信

撰写区固定在右栏底部，时间线单独滚动。选中 Alice 后即可输入。每封历史消息提供「引用」，包括自己发出的邮件。草稿区从上到下依次展示可取消的引用条、收件人和主题、正文、待发附件、保存状态与「发送」。在较窄窗口中允许地址和附件换行。正文使用纯文本，Enter 换行，点击「发送」才提交。

| 用户操作 | 撰写区与出站邮件 |
| --- | --- |
| 直接给 Alice 写信 | To 为 Alice，主题默认取正文第一行并去除首尾空白，第一行仍保留在正文里。正文变化时同步更新自动主题。手动修改主题后以手填值为准。 |
| 点旧询价的「引用」 | 引用条显示原发件人、主题及一行可读摘要。立即显示该邮件推导出的收件范围和回复主题。切换引用对象时保留已写正文和待发附件。引用条可跳到原邮件。 |
| 回复主题 | 继承原主题，已有回复前缀时沿用，否则添加一次 `Re: `。原信主题为空则允许填写。用户可手动修改，回复关系仍指向所选消息。 |
| 点引用条的 × | 保留正文与附件，To 恢复为当前联系人，清空回复带来的 Cc。恢复引用前手填的新邮件主题，如此前使用自动主题，则按当前正文首行重新生成。 |
| 点击「新会话」输入地址 | 已有地址恢复其会话和草稿。新地址打开临时会话。只打开或写草稿均不会加入「最近会话」，首封发送被接受后在同一窗口转为正式会话。 |
| 选择附件 | 系统选择器支持多选，复制完成后显示文件名、大小和移除按钮。原文件移动或删除后仍可发送。只发送用户本次添加的文件。 |
| 点击「发送」 | 发送前可见实际 To、Cc、主题及附件。须有可用收件人、非空主题，以及非空正文或至少一份附件。只有附件时可手填主题后发送。文件复制中或草稿保存失败时给出具体原因。 |

**例子**　Alice 周一询价并抄送 Bob，周三又发来另一份目录。周四在同一会话直接写「周五送样」会发起新邮件。点击周一那封的「引用」会回复周一的询价。此时点「回复全部」，发送前会看到 Alice 在 To、Bob 在 Cc。

## 2. 收件范围与引用关系

| 引用对象 | 默认收件人 | 「回复全部」 |
| --- | --- | --- |
| 对方发来的邮件 | 优先使用原信有效的 `Reply-To`，缺省时用 `From`。回复地址与联系人邮箱不同时，撰写区展示实际地址。 | 保留默认回复对象，将原 To 的其他外部收件人加入 To，原 Cc 加入 Cc。 |
| 自己发出的邮件 | 默认给当前会话联系人，避免回复到自己。 | 使用原 To、Cc 中的外部地址。 |
| 地址清理 | 使用账号现有地址键去重，移除托管账号自身，To 优先于 Cc，保留显示名与原顺序。 | 有额外收件人才显示开关。原信的 Bcc 不带入。 |

主进程按本地 `quoted_message_id` 读取所选消息并核验会话归属。出站邮件使用新的 `Message-ID`。引用时，`In-Reply-To` 取原邮件的互联网 `Message-ID`，`References` 在原有有效引用链后追加原标识并去重。普通新邮件的两个引用头均省略。若原件缺少有效的互联网标识，保留本地引用卡并提示「此邮件缺少回复标识，对方邮箱可能无法归入原会话」。

**建议首版回复正文只发送撰写区可见的用户文字**，收件方可通过标准邮件头串起会话。FTCS 发出的本地消息新增可选 `quoted_message_id`，阅读时优先按同账号本地 ID 跳转。其他客户端发来的回复继续沿用已有头部解析与引文折叠。用户若需要将原信某段文字发给新加入的收件人，可将该段放入正文。

## 3. 草稿与附件如何落盘

沿用账号目录 `data/mail/accounts/<account_id>/`。主进程是唯一写入者，旧工作区第一次写草稿时按需创建目录。

| 位置 | 本故事的读写约定 |
| --- | --- |
| `contacts.jsonl` | 新地址首次产生草稿时按地址键查找或分配稳定的 contact_id。与新来信导入共用账号写入顺序，同一地址复用同一记录。正式列表成员仍由已发生的邮件往来决定。 |
| `drafts/<contact_id>.json` | 使用模型已有的 draft_id、rev、mode、to、cc、subject、subject_mode、text_body、quoted_message_id、attachments、updated_at。补充可选 `new_subject_override`，保存切换到引用前手填的新邮件主题。读取老文件时该字段视为空。 |
| `attachments/<attachment_id>/content` | 系统选择器和文件复制在主进程完成。每个文件使用独立 UUID，先写临时文件、原子改名，再把描述加入草稿。按项提示复制失败，可保留本批已成功的文件。同名文件可区分、可单独移除。 |
| `sends/<YYYY-MM>.jsonl` | 月份取尝试创建时的 UTC 月份。后续结果始终追加到同一分片。首条记录保存 request_id，并冻结草稿版本、发信账号、地址、引用、主题、正文、附件 ID、两个消息 ID 和发送时间。 |
| `messages/<YYYY-MM>.jsonl` | 服务器接受后，使用冻结的本地消息 ID 生成一条 outgoing 消息，归属发起会话。多收件人细节保存在地址字段中。已发送副本到达时复用这条消息。 |

- 页面在输入短暂停顿后合并保存，建议 300 ms。切换联系人、离开邮箱、正常关闭窗口、发送前立即提交最后的修改。只有主进程确认落盘才显示「草稿已保存」。异常退出可恢复最近一次已确认版本。
- 每个写操作携带 draft_id 和 expected_rev，同一草稿的请求顺序执行。旧版本写入返回冲突和当前版本，页面保留尚未保存的输入。同步事件只刷新列表摘要和时间线，不能用旧快照覆盖正在输入的正文。
- 选中已有联系人时自动恢复草稿。有往来的联系人左栏显示「草稿」和摘要。对于只有草稿的新地址，「新会话」入口列出该账号的待写地址，点击即可恢复，重启后也能找到。正文、手填主题、附件及引用均清空时，删除空草稿。
- 移除附件先更新草稿。已冻结的发送快照和已发消息可继续持有相同附件。清理时先核验引用。取消选择器只关闭弹框。工作区或账号变化时终止旧页面请求，已完成的 A 账号草稿只在重新托管 A 时恢复。

## 4. 点击发送后会发生什么

| 主进程状态 | 撰写区 | 时间线和联系人列表 |
| --- | --- | --- |
| `submitting` | 显示「正在发送」，锁定本次草稿的发送按钮。用户可以切换会话。 | 发送状态依附于草稿。此时收到新邮件仍照常刷新。 |
| `accepted` | 显示「已发送」，清除与此次 draft_id 和 rev 均匹配的草稿，恢复新邮件输入。 | 立即按本地消息 ID 追加一条本方消息。新地址此时进入列表。已发送表示发件服务器已接受。 |
| `failed` | 显示原因并保留可编辑草稿，例如认证被拒、服务器明确拒绝整封邮件。用户可修改后再次点击。 | 保留原列表及往来记录。 |
| `unknown` | 显示「发送结果待确认」，保留本次原文、附件和收件范围。提示查看已发送文件夹。 | 保留待确认记录。重新打开应用或点击同步只做核对，均不会触发再次投递。 |

**SMTP 判定**。复用连接验证的 TLS、认证配置和凭据读取方式，通过 Nodemailer 提交。以邮件数据提交后的最终接受响应作为成功依据。明确提交前失败或服务器明确拒绝可判为失败。数据可能已提交但最终回执丢失时记为未知。遇到无法确定阶段的异常也按未知处理。多人邮件允许出现部分接受：数据提交已确认时记录为 accepted，同时持久化接受与拒绝的信封地址，界面显示「部分收件人未接受」及地址，已发消息保留原 To/Cc 和结果明细，不提供整封重试。缺少最终回执时保留已经明确拒绝的地址，其余地址待确认。

**幂等与恢复**。每次用户发起发送生成一个 request_id，用于 IPC 超时后的同请求查询或重放。同一草稿版本已有进行中、已接受或待确认尝试时，返回已有尝试。明确失败后，用户主动重试才产生新的 attempt_id 和出站 Message-ID。同账号的发送记录、本地消息和导入提交共用写入队列。网络等待放在队列外。

1. 校验活动工作区、账号、连接批次、草稿版本、实际收件人和全部附件。冻结快照，分配 attempt_id、本地 message_id 和出站 Message-ID，追加并刷盘 submitting。此步失败直接返回，SMTP 尚未开始。
2. 只从冻结快照构造邮件及信封。终态写回前再次核验上下文。若用户已断开或切换工作区，关闭旧传输，保留原账号记录待恢复。迟到的回执不得改写新账号。
3. 明确接受后先追加 accepted，再按本地 ID 补写消息、更新索引、清理匹配的草稿，最后广播 `mailbox.changed`。若此时磁盘写入失败，提示记录待恢复，禁止按发送失败重发。
4. 重启时逐一补齐已接受记录对应的消息和草稿清理。缺少终态的 submitting 恢复为 unknown。恢复可重复执行，且只涉及本地数据和副本核对。

## 5. 已发送副本如何合并

当前导入器以服务器副本键和「互联网 Message-ID + 原始 MIME 字节摘要」识别重复导入。FTCS 的本地发送记录没有那份服务器原始字节。实现时在已发送文件夹导入流程中，**先核对本地发送尝试，再创建联系人、附件和逻辑消息**。[现有导入路径](../../desktop/electron/mailbox/import.ts)

- 以同账号、发送角色、固定出站 Message-ID 查唯一候选。再比较本方发件地址、To/Cc 地址集合、主题、解码后正文（统一换行）及附件内容摘要。发送时可在快照记录这些特征。传输编码、头字段顺序或服务商新增跟踪头不影响匹配。
- 命中时将服务器的 folder_id、UIDVALIDITY、UID 映射到冻结的本地 message_id。若同步先于 SMTP 回调，双方复用同一尝试和消息 ID。可靠命中的副本可将 unknown 收敛为 accepted，标记依据为「已发送副本核对」。SMTP 仍在提交时先记录副本证据，等待回调补充结果。重启恢复时也检查已保存的匹配证据。只有 SMTP 有明确逐地址回执时才显示逐收件人接受情况。副本可证明邮件已出现在已发送文件夹，无法证明每位收件人均已接受或送达。
- 找不到唯一候选、内容冲突或服务商重写标识时，保留服务器邮件并沿用普通导入，待确认尝试继续可查。同主题与相近时间不足以认定同一封。服务商没有自动保存副本或已发送文件夹尚未绑定时，SMTP 已接受的邮件仍可在 FTCS 阅读。本故事按现有方案读取服务器副本，不主动向 IMAP 追加第二份。

## 6. 页面与主进程接口

复用 `window.ftcs.mailbox`、现有 IPC 来源检查及 `Context + accountId` 校验。发件身份、授权码、文件系统路径和最终邮件头由主进程持有。[现有接口](../../desktop/electron/mailbox/types.ts) · [连接验证](../../desktop/electron/mailbox/protocol.ts)

下表列出逻辑操作。实际调用统一使用 `composer(ctx, accountId, email, action)`，其中 `action.kind` 依次为 `get`、`save`、`pick / remove`、`send`。新会话菜单通过 `temporaryDrafts(ctx, accountId)` 读取待写地址。[请求与返回类型](../../desktop/electron/mailbox/compose-types.ts)

| 调用 | 输入与返回 |
| --- | --- |
| `getComposer` | 以 contactId 或新会话地址打开，返回地址、草稿或空白撰写状态、当前尝试及结果。打开空白会话只读。另提供仅含地址与摘要的临时草稿列表供「新会话」恢复。 |
| `saveDraft` | 传目标联系人或临时地址、草稿身份与预期版本、正文、主题编辑意图及引用模式。主进程解析原件与 To/Cc，返回已持久化的新版本及实际收件范围。快速切换引用时，只有最新意图的响应能更新撰写区。 |
| `pickDraftAttachments / removeDraftAttachment` | 对已定位的草稿选择系统文件或按 attachment_id 移除，返回新版本和附件摘要。首次添加前可创建草稿。取消后清理空草稿。 |
| `sendDraft` | 传 draft_id、expected_rev、request_id 与用户刚看到的 To/Cc。如果校验所得地址有变化，返回最新撰写状态让用户核对。返回 attempt_id 和状态，页面通过变更事件重读结果。 |
| `conversations / timeline / changed` | 最近会话扩展可选草稿摘要。消息详情扩展本地引用及部分接受的地址明细。草稿变更只需更新对应会话，保持阅读位置。 |

## 7. 交付与联测

建议在本故事内先完成本地撰写与草稿恢复，再接 SMTP 发送与本地回显，最后把发送尝试接入已发送同步并验证恢复。US-MAIL-04 继续负责已读写回、跨客户端标记同步和提醒。US-MAIL-05 复用同一个发送服务接入审核页及结果处理。

| 验收场景 | 可观察的结果 |
| --- | --- |
| 在已有会话直接写，再对周一旧邮件点引用、取消引用、重新引用 | 新邮件按第一行生成主题，可手改。取消后保留文字、附件和原手填主题。接收邮箱查看邮件源，回复头指向周一那封，新邮件无引用头。 |
| 多人来信含 Reply-To、重复地址、本账号及密送。再引用一封本方发件 | 默认回复、回复全部及本方发件的地址与第 2 节一致。提交的信封与确认前展示一致。 |
| 新地址只打开、写草稿后重启、再发出首封 | 先无空联系人。从「新会话」找回草稿。成功后原窗口和最近会话显示同一条发件。 |
| A 账号分别给 Alice 和 Bob 写草稿，附同名文件，移走本机源文件，再切账号并重启 | 文本、引用、收件范围和正确的附件字节分别恢复。B 账号看不到 A 的草稿，较晚返回的旧请求不能覆盖新内容。 |
| 连点发送，分别模拟全部拒收、部分接受、提交后断线 | 每次有效操作只提交一次。明确失败可手动重试。部分接受逐地址说明。未知保留原文。重启不会重复发送。 |
| SMTP 回执、已发送同步按两种顺序到达，或在 accepted 后强制退出 | 同一邮件最终只有一条时间线消息。迟到副本只补映射。中断恢复只清理已发送版本的草稿。 |
| 服务商不保存副本，或另一封邮件与尝试同主题但内容有差异 | 已明确接受的本地发件仍可读。冲突副本不与待确认尝试强行合并。 |

开发阶段用可控的 SMTP/IMAP 测试端覆盖拒收、部分接受、丢回执及重放。测试邮箱联测重点查看对方实际收到的主题、引用关系、附件，以及服务商已发送副本同步回 FTCS 后的条数。
