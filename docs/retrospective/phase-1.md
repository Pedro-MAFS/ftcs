# Phase 1 复盘

> 复盘日期：2026-07-12  
> 状态：Phase 1 MVP 闭环已全部验收通过

---

## 1. 阶段目标回顾

Phase 1 的目标是跑通一条可重复的外贸获客流水线：

```
产品信息输入 → 产品画像 → 关键词扩展 → R1 探索 → 线索评分去重 → 意向邮件草稿 → 人工审核
```

**结论：目标已达成。** 系统已能在智能体环境中，从一家公司的网站或资料出发，自动发现潜在客户、整理优先级，并生成可审核的开发信草稿。

## 3. 什么做对了

### 3.1 「智能体负责判断，工具负责执行」

- 探索、评分、存储等确定性逻辑放在 MCP / 规则引擎中
- 智能体专注于：读页面、判断是否目标客户、润色邮件
- 结果可测试（lead-store 16 项测试、search-api 5 项测试）

### 3.2 文件约定 + Schema 先行

- 所有中间产物落在 `data/` 下，结构清晰
- 换 IDE 不丢数据，便于调试与审计
- 每个阶段有明确输入/输出路径

### 3.3 小步迭代、每步可验收

- 1.1 → 1.5 分五段交付，每段独立验收
- 降低了「做大做全」的风险
- 问题可以早期暴露（如 chrome-devtools 替代 web-crawler 的决策）

### 3.4 人机协作设计

- 邮件默认「待审核」，不自动群发
- 线索带 `match_reason` 和 `personalization_evidence`，用户可判断 AI 是否找对人

## 4. 核心问题：学习成本过高

### 4.1 现象

Phase 1 的**运行环境是开发者工具**（Cursor、OpenCode、Codex 等）。对开发同学来说，MCP、Skill、`.cursor/mcp.json` 是日常概念；但对**外贸业务员、外贸经理**来说：

| 概念 | 开发同学 | 业务用户 |
|------|---------|---------|
| MCP | 工具接口，能配 | 「这是什么？」 |
| Skill | 工作流说明 | 「我还要学这个？」 |
| 对话触发 | 自然 | 不知道说什么、怎么说 |
| 重启 MCP | 常规操作 | 完全不可接受 |
| 看 JSON 文件 | 正常 | 头疼 |
| 配置 API Key | 能搞定 | 容易放弃 |

**一句话：我们做出了「能用的系统」，但没有做出「能用的产品」。**

### 4.2 根因

Phase 1 有意选择了**智能体原生路径**以快速验证业务闭环，这是正确的工程决策；但验证结果表明：

> **业务能力已初步成立，产品形态尚未成立。**

当前用户路径：

```
安装 Cursor → 配置 MCP → 配置 Tavily Key → 学习 Skill 触发语
  → 对话执行 5 步 → 打开 data/ 目录看 JSON → 人工找邮件草稿
```

这对「会用 AI 的开发者」可行，对「只想找客户的外贸人」几乎不可用。

### 4.3 影响

- 系统无法交给非技术同事独立使用
- 销售/培训成本极高
- 口碑传播困难（「好用但太复杂」）
- Phase 2 的自动化（定时探索、发信）若仍绑 IDE，价值大打折扣

## 5. 战略结论：必须补一层可视化界面

### 5.1 原则

**底层不变，界面补上。**

- 保留现有 MCP + Skills + `data/` 约定作为**引擎层**
- 新增 **Web 控制台** 作为**产品层**，把五步流水线变成「点按钮」

```
┌─────────────────────────────────────────┐
│         Web 控制台（产品层）               │
│  上传网站 │ 一键探索 │ 线索列表 │ 审邮件    │
└──────────────────┬──────────────────────┘
                   │ API / 直接读写 data/
┌──────────────────▼──────────────────────┐
│    引擎层（Phase 1 已有，继续复用）         │
│  lead-store │ search-api │ Skills 编排    │
└─────────────────────────────────────────┘
```

业务用户**不需要知道** MCP 和 Skill 的存在；开发同学仍可直接用 Cursor 调试引擎。

### 5.2 建议的界面模块（Phase 2 / 2.5）

| 页面 | 用户操作 | 背后调用 |
|------|---------|---------|
| **产品_setup** | 输入公司网站 URL，点击「提取画像」 | `extract-product-profile` |
| **产品画像** | 查看/补全目标市场、买家类型 | `product_save` |
| **关键词** | 一键扩展，可编辑搜索词 | `keywords_expand` |
| **探索** | 选择 R1，点击「开始探索」，看进度 | `discover-leads` |
| **线索库** | 表格：公司、分数、tier、匹配理由 | `scored.json` 可视化 |
| **邮件审核** | 左右分栏：线索信息 + 邮件草稿，改字、通过 | `draft.json` + 审核流 |
| **设置** | Tavily Key、发信邮箱（Phase 2） | 配置页，不写 json |

### 5.3 交互原则

1. **零 IDE** — 业务用户从不打开 Cursor
2. **零 JSON** — 所有数据用表格、卡片、表单呈现
3. **一键流水线** — 提供「从头跑到邮件」的向导模式
4. **状态可见** — 探索进度、API 用量、线索数量实时展示
5. **引擎可分离** — UI 通过 HTTP API 或直接读 `data/`，不绑死 Cursor

## 8. Phase 2 优先级建议（修订）

> **架构决策（2026-07-12）**：采用 **Electron + OpenCode CLI Sidecar** 模式。详见 [08-产品架构决策-Electron-OpenCode.md](../08-产品架构决策-Electron-OpenCode.md)。

结合复盘，建议 **调整 Phase 2 顺序**：

| 优先级 | 任务 | 理由 |
|--------|------|------|
| **P0** | Electron 壳 + OpenCode Sidecar 集成 | 产品载体 |
| **P0** | 外贸 Web UI（产品录入 + 线索库 + 邮件审核） | 解决学习成本 |
| P1 | `email-sender` 审核后发送 | 闭环触达 |
| P1 | `scheduler` 定时探索 | 自动化 |
| P2 | R2/R3 多轮探索 | 深挖掘 |
| P2 | SQLite 迁移 | 为 UI 并发读写作准备 |
| P3 | PDF/Excel 解析 | 降低输入门槛 |

原 Phase 2 计划中的「简易审核界面」应从「可选」升级为 **P0 必做**。

## 9. 技术路线建议（控制台）

**已确认方案：Electron + OpenCode CLI Sidecar**（详见 [08-产品架构决策-Electron-OpenCode.md](../08-产品架构决策-Electron-OpenCode.md)）

| 层 | 技术 |
|----|------|
| 桌面壳 | Electron |
| 智能体引擎 | OpenCode CLI（`opencode serve`，Sidecar） |
| 外贸 UI | Vite + React/Solid（Electron Renderer） |
| 工具链 | Phase 1 MCP + Skills（不变） |
| 数据 | 本地 `data/`（Phase 2 后期 SQLite） |

MVP 控制台最小范围（4–6 周）：

1. Electron 启动/停止 OpenCode Sidecar
2. 产品录入页（网站 URL → 画像）
3. 一键探索 + 进度条
4. 线索列表（按 tier 筛选）
5. 邮件审核页（编辑 + 标记通过）
6. 设置页（Tavily Key、LLM Provider）

## 10. 总结

### 我们证明了什么

- 外贸获客全流程可以用 AI + 工具链自动化
- 从网站到邮件草稿的路径真实可行
- MCP + Skills 是优秀的**引擎**，适合快速迭代

### 我们缺什么

- 面向业务用户的**产品界面**
- 低学习成本的操作路径
- 与 IDE 解耦的部署方式

### 下一句话

> **Phase 1 验证了「能不能做」；Phase 2 用 Electron + OpenCode 回答「好不好用」。**

控制台不是可选项；产品形态已确定为 **Electron 桌面 App + OpenCode CLI Sidecar**。
