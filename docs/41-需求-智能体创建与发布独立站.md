## 1. 目标

让外贸用户在 FTCS 内通过智能体创建、预览、修改和发布自己的独立站。网站项目由智能体按用户要求编写，使用客户自己的 GitHub 仓库保存源码，通过客户自己的 Cloudflare 发布，并支持绑定客户自有域名。

用户可以让智能体参考现有产品画像和资料库，也可以直接用聊天补充需求。用户决定网站的页面结构、内容和视觉方向。

## 2. 已确认的产品方向

1. **一个工作区一个全局站点项目**。站点不绑定某个产品画像。用户可以选择使用零个、一个或多个产品画像，也可以引用资料库文件和用户直接提供的内容。切换当前产品不切换站点。
2. **项目形态是可构建的纯前端 Node.js 项目**。不限定单页、多页、产品详情页、前端框架或源码组织方式，由用户与智能体决定。
3. **项目必须支持预览和构建**。项目提供 npm run dev 用于本地预览，提供 npm run build 用于生成线上静态文件。站点项目需记录构建产物目录，供发布使用。
4. **账号和资产归用户所有**。使用用户自己的 GitHub 和 Cloudflare 账号。用户持有或管理站点仓库、Cloudflare 项目和自有域名。
5. **首期提供联系入口**。网站可展示用户确认的邮箱、电话、WhatsApp 等联系方式。站内提交和保存询盘后续再支持。
6. **支持自有域名**。用户可以将自己的域名绑定到 Cloudflare 上的站点，并查看绑定进度。
7. **智能体持续维护站点**。用户可通过聊天提出新建、修改、增加页面或调整内容等要求，再预览和发布更新。

上述内容是本草案的产品方向。具体页面布局、技术接线、授权方式和版本安排留待核对及详设。

## 3. 用户与使用场景

主要用户是没有独立站，或希望基于已有产品资料快速建立展示网站的外贸企业。用户可能不熟悉前端开发、GitHub、Cloudflare 或 DNS。

典型场景：

- 用户已有公司和产品画像，希望生成英文企业站，用于展示公司及主要产品。
- 用户有多份产品画像和资料库图片，希望在同一站点介绍不同产品，并通过对话决定是否增加产品详情页。
- 用户希望调整已生成网站的文案、配色、图片或页面结构，先在本机预览，再更新线上站点。
- 用户已有自己的域名，希望将其绑定到已发布的网站。

## 4. 主要使用流程

1. **进入独立站功能**。用户在 FTCS 中找到全局站点入口，创建站点项目或继续维护已有项目。入口位置和界面形式待设计。
2. **描述建站需求**。用户通过智能体说明业务、语言、页面内容、风格和联系方式；可按需选择产品画像和资料库材料。
3. **生成或修改项目**。智能体在站点项目中编写前端代码、页面内容和配置，必要时向用户补充提问。
4. **本地预览**。系统准备依赖、启动 npm run dev，在应用内展示网站，并反馈启动和运行状态。用户可继续与智能体对话修改。
5. **连接用户账号**。用户连接自己的 GitHub 和 Cloudflare，并按流程完成必要授权，选择或创建站点仓库和 Cloudflare 项目。
6. **构建并发布**。系统检查网站构建和发布配置，将站点项目提交并推送到用户选择的 GitHub 仓库，跟踪 Cloudflare 构建和部署结果。
7. **访问与域名**。部署成功后展示可访问地址。用户可绑定自有域名，按状态提示完成 DNS 配置与验证。
8. **维护和再次发布**。用户继续修改网站，预览后发起下一次发布，并查看结果。

以上为目标流程，首次连接和后续发布的具体操作步骤待技术验证。

## 5. 功能需求

### 5.1 全局站点与项目

- 一个 FTCS 工作区维护一个全局站点项目。当前站点状态在不同产品页面和聊天之间可访问。
- 站点项目位于工作区内明确的独立目录。具体目录名和组织方式交详设确定。
- 同一站点可使用多份产品画像、资料库资料和用户直接输入的信息。
- 站点项目维护自己的源码和配置。产品画像或资料库后续变化时，站点如何发现变更、何时同步，由后续方案确定；已有网站内容的更新由用户发起。
- 系统记录项目的位置、依赖和构建配置，以及预览、发布和域名管理所需的关联信息。
- 已有项目在重启应用后仍可继续预览、编辑和发布。
- 当项目缺失、损坏或脚本不符合要求时，向用户说明原因，并允许用户通过智能体修复后重试。

### 5.2 内容来源与用户确认

- 智能体可以读取用户选定的产品画像和资料库资料，结合聊天内容生成和修改网站。
- 用户可以选择图片作为公开展示素材，也可以让智能体根据用户指示挑选并交由用户确认。
- 原始产品资料、联系人信息及其他工作区数据是否公开，取决于用户对网站内容的选择。生成项目只纳入网站需要的文件；发布前应让用户能够检查待发布内容。
- 用户可查看并修改对外展示的公司介绍、产品、联系方式等内容。资料不完整时，智能体应根据上下文向用户提问，或标明缺失内容，供用户补充。
- 内容生成与页面结构由用户需求和智能体共同确定。首期不限定网站必须使用某种模板或固定页面数量。

### 5.3 前端项目约定

站点项目至少满足：

- 项目是可使用 Node.js 和 npm 管理的纯前端项目。
- package.json 提供 npm run dev，供本地预览。
- package.json 提供 npm run build，生成可用于静态托管的线上文件。
- 系统知道项目根目录及 npm run build 的静态产物目录。产物目录可由项目配置或用户确认，不限定具体目录名。
- 成功构建后，发布所需的页面、样式、脚本、字体和图片等资源可以由 Cloudflare 托管和访问。
- 站点线上访问无需依赖用户本机或 FTCS 桌面进程。

依赖安装、预览服务进程、端口识别、项目脚本兼容性和静态产物校验的具体机制待详设。目标是让 FTCS 能向用户呈现可用预览、构建结果及可理解的失败信息。

### 5.4 智能体编写与权限

- 用户可以通过智能体创建和修改站点项目，包括源码、样式、资源和前端项目配置。
- 为实现网站编写、安装依赖、启动预览和构建，需要在站点场景中提供受控的文件操作及命令执行能力。
- 操作范围、允许的命令、依赖安装、网络访问、用户授权以及异常终止的具体设计须与现有权限规则协调。不能仅靠提示词约束实际操作范围。
- 网站项目与 GitHub、Cloudflare 凭据分开管理。凭据不能进入智能体生成的网站代码、日志或提交内容。
- 建站与发布的任务状态应与当前智能体任务生命周期及页面状态接线协调。是否拆为多个任务、使用哪些任务类型和状态，由详设确定。

现有系统默认拒绝 edit、bash 等操作。站点开发对工作区文件和命令的需求与现有约束存在差异，需要先验证实际权限机制，再确定可执行方案。

### 5.5 本地预览

- 用户可以启动、打开和停止当前站点的本地预览。
- FTCS 能识别并展示实际可访问的预览地址，在应用内浏览器打开。
- 用户修改网站后可以继续查看更新。热更新由具体前端项目的开发服务决定。
- 界面应区分预览启动中、运行中、已停止和失败，并提供失败原因与重试方式。
- 依赖未安装、端口占用、脚本缺失、服务提前退出和应用关闭等情况需要有明确处理。
- 用户停止预览或退出应用后，应正确管理本次预览产生的进程。

### 5.6 GitHub 仓库

- 用户授权自己的 GitHub 账号，并选择仓库归属和仓库。
- 目标流程支持用户选择已有仓库或创建站点仓库。个人账号和组织账号的权限、创建方式及可选范围待技术验证。
- 系统记录仓库、分支、远端地址以及最近一次同步信息，供后续发布使用。
- 发布前让用户知道将写入的仓库、分支和内容；处理用户在 GitHub 上直接修改、远端分支已变化及推送冲突等情况。
- 当授权过期、仓库无权访问、网络失败或推送失败时，显示可操作的错误信息，支持重新授权或重试。
- 仓库的可见性由用户选择。最终写入范围和发布文件的确认方式待详设。

### 5.7 Cloudflare 发布

- 用户使用自己的 Cloudflare 账号，授权或连接所需的 Cloudflare 项目与目标 GitHub 仓库。
- 首次发布时选择或创建与该站点对应的 Cloudflare 项目，配置生产分支、构建命令和静态产物目录。
- 用户发起发布后，系统完成所需的项目构建与 GitHub 推送，并获取 Cloudflare 构建和部署结果。
- 页面应分别反映源码同步与 Cloudflare 部署状态。只有目标版本完成部署，才显示该版本发布成功和可访问地址。
- 发布失败时保留本地项目和失败信息，允许修复后重试；重复操作及部分步骤成功后的恢复方式待详设。
- 用户再次发布时沿用已确认的站点与仓库关联，允许用户检查目标信息。
- Cloudflare Git 授权、项目创建和绑定能自动完成到什么程度，须先通过真实账号验证。遇到需要客户在 GitHub 或 Cloudflare 完成的授权操作时，应用应给出明确指引和可恢复的后续步骤。

### 5.8 自有域名

- 用户可以为已关联的站点添加自己的域名，并查看当前绑定状态和需要执行的步骤。
- 系统应根据实际接入方式，提示用户完成域名所有权验证和所需 DNS 配置。
- 用户可查看待配置、验证中、已生效或失败等实际状态，以及相应原因或后续操作。
- 是否支持根域名和子域名、用户已有 DNS 配置的处理、域名更换或解除绑定等细节，需在技术验证和用户流程设计中确认。

### 5.9 站点管理与状态

站点入口应帮助用户了解当前站点和下一步可执行的操作，包括：

- 项目存在与否、当前预览状态、最近构建结果。
- GitHub 账号、仓库和分支的连接状态。
- Cloudflare 账号、项目、最近一次部署状态和线上地址。
- 自有域名、验证进度和访问地址。
- 失败原因、重试或重新授权入口。

状态刷新、应用重启和网络中断后，以本地项目和相关服务的实际结果恢复展示。用户在智能体中继续修改时，应能理解修改尚未发布还是已经发布。

## 6. 首期边界

首期网站以纯前端静态项目构建和发布。联系入口使用用户确认的信息；站内提交、接收和保存询盘后续支持。

首期围绕一个工作区一个全局站点项目设计。网站使用客户自己的 GitHub 与 Cloudflare 账号，并支持客户自有域名。

页面数量、前端框架、视觉风格和组件组织由用户要求与智能体生成结果决定。具体支持的 Node.js 版本、依赖和可运行命令，由技术验证及详设明确。

## 7. 验收草案

用户故事拆分与建议推进顺序见 [独立站需求拆分与交付顺序](独立站-需求拆分与交付顺序.md)，拆分已验收，后续逐项进行技术验证与详设。

本节用于核对产品方向，详细验收数据和测试步骤在需求拆分后补充。

1. 用户在同一个工作区创建站点后，切换产品仍能找到并继续维护同一个站点。
2. 用户可以用自然语言要求不同页面结构，包括单页和带产品详情页的网站；项目包含可运行的 npm run dev、npm run build 和明确的静态产物目录。
3. 用户可以选择产品画像和资料库资料，智能体按用户要求生成可检查、可修改的网站；发布内容可供用户确认。
4. 用户能启动本地预览，在应用中打开网站，修改后再次查看；启动失败及端口或依赖问题有明确反馈。
5. 用户能连接自己的 GitHub 与 Cloudflare，通过目标流程发布网站，并在 Cloudflare 部署成功后获得访问地址。授权、推送、构建和部署失败都能区分并处理。
6. 用户能为站点发起自有域名绑定，看到 DNS 配置或验证步骤，并确认域名实际生效状态。
7. 用户能在本地再次修改、预览和发布，线上版本与用户本次确认的发布版本对应。
8. 站点提供用户确认的联系方式入口；凭据和未经选择的原始资料不会被作为网站文件提交。
9. 应用重启、预览停止、部署失败、远端仓库更新及授权失效后，站点项目和状态能按设计恢复或给出明确处理方式。

## 8. 技术验证与待核对事项

以下事项需要验证或由用户与产品、研发共同决定，不作为已实现能力：

1. **运行和权限边界**：如何让智能体在站点目录内修改代码、安装依赖、启动和停止进程，同时与现有权限机制及任务生命周期兼容。
2. **GitHub 用户授权**：账号授权方式、最小权限、个人与组织仓库创建、已有仓库写入及授权撤销后的体验。
3. **Cloudflare 接入**：对比 Cloudflare 当前支持的静态站点 Git 集成方案；验证从用户授权、仓库关联、项目创建、构建配置到部署状态查询的完整链路，确认哪些步骤可由 FTCS 完成、哪些需要用户在外部页面操作。
4. **构建与预览契约**：支持的 Node.js / npm 版本、依赖安装方式、端口和地址识别、构建产物目录记录、单页或多页路由在静态托管下的行为。
5. **域名**：根域名、子域名、不同 DNS 托管商的绑定和验证路径，以及状态查询。
6. **站点与数据同步**：工作区迁移、站点项目遗失或已有 GitHub 仓库变更后的恢复方式；画像或资料库变化后如何提示用户更新网站。
7. **费用和限额**：GitHub、Cloudflare、用户自有域名及模型调用可能涉及的计划、配额或费用，按实际选型和用户账号核对。
8. **询盘后续能力**：提交、接收、存储、反垃圾及与现有线索库的关系，留待后续单独设计。
