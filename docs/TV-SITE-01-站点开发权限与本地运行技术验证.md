# TV-SITE-01 站点开发权限与本地运行技术验证

状态：**进行中，尚未通过**。本机与 Windows 基础实验已执行；真实桌面端联动及隔离方案原型尚待验证。本文对应[交付顺序中的 TV-SITE-01](./独立站-需求拆分与交付顺序.md#tv-site-01站点开发权限与本地项目运行)，是技术验证记录，不是产品功能已交付的声明。

## 1. 验证目标与范围

验证智能体能够在受控范围内编辑一个全局站点项目，安装依赖、执行 `npm run dev` 和 `npm run build`，并让桌面端可靠地管理和打开预览。站点可以使用任意满足项目契约的纯前端 Node 项目；不能把安全边界建立在生成代码或依赖均可信的假设上。

**站点目录约束：** 每个 FTCS 工作区在其内部约定一个固定子目录，作为该工作区唯一的全局站点项目根目录；站点源码、项目依赖、开发服务的工作目录和构建产物在此范围内管理，切换产品不切换站点。具体目录名和迁移规则在后续详设中确定。桌面端提供的 Node/npm 可以位于工作区之外，作为运行工具使用，不要求复制到站点目录。

“以站点目录作为工作目录”不等于系统隔离：项目代码、依赖、安装钩子及其子进程仍可能访问工作区其他内容或外部路径。验证需要以实际工作区结构和其他目录中的无敏感测试标记确认隔离边界。

验证需要回答：现有权限如何接入；项目代码和安装脚本能访问什么；如何避免访问资料、凭据及其他工作区数据；如何控制子进程和网络；如何获取真实监听地址、识别构建产物、停止进程和处理异常；上述行为在 Windows 上是否成立。GitHub、Cloudflare 和域名链路分别在 TV-SITE-02/03 验证。

## 2. 当前实现与关键发现

- 仓库 `workspace/config/opencode/opencode.json` 默认拒绝通用编辑、命令和外部目录访问；`desktop/electron/opencode/permission-gate.ts` 对相关权限设硬边界。`task-context.mjs` 的任务约束针对特定工具调用，不能为任意 npm 脚本提供操作系统级隔离。现有自动测试通过，不代表真实模型、真实桌面或操作系统隔离已经验证。
- 本机实验中，普通 `npm install` 的生命周期脚本以及 `npm run` 都能写入站点目录外的**临时测试目录**。因此仅设置工作目录、限制智能体工具参数或允许 `npm` 命令，不能限制脚本及其依赖的文件访问。安装带 `--ignore-scripts` 阻止了测试包的安装钩子，但之后的 `npm run` 仍可运行代码；不能据此推断所有项目依赖都兼容该选项。
- Node 权限模式在本机阻止了 Node 进程直接、经符号链接和通过 Node 子进程的测试写入；在允许启动子进程的情况下，原生 `cp` 子进程仍能写出目录。Node 权限模式因此不能单独作为运行不受信任项目的安全边界；这只是本机实验，不推断 Windows 的结果。
- `desktop/electron/browser-runtime/cdp-filter.ts` 把 `localhost:5173` 和 `127.0.0.1:5173` 判为应用自身页面，排除在相关 CDP 页面接纳和过滤逻辑之外。实际桌面预览能否显示及智能体能否操作，需要在桌面端复测，不能仅凭过滤函数推断整个预览界面的行为。

## 4. 建议进入原型的技术方案

1. **建站任务授权**：以当前工作区固定站点子目录作为建站项目根目录，保留其他任务现有权限。建站能力通过明确的任务上下文和受控接口提供站点文件读写、启动、停止、构建与状态查询；输入路径先作规范化和真实路径检查，并处理符号链接、竞态等问题。不得仅通过放开通用 `bash` 或全局 `edit` 达到建站目的。产品资料经明确选择后导入站点可访问的范围，凭据不注入项目进程。
2. **项目执行隔离**：将安装、构建和开发服务视为可执行第三方代码，在单独的受限运行环境执行。Windows 优先验证受限身份／AppContainer 等操作系统隔离、目录 ACL、子进程限制、Job Object 生命周期及网络策略能否组合满足要求；具体 API 和兼容性须以原型实测确认。普通 `cwd`、字符串路径检查、单独的 Node 权限和命令白名单均不足以证明隔离。隔离范围应覆盖环境变量、继承句柄、配置文件、工作区数据、IPC、其他本地服务与凭据；按依赖下载及本地预览所需设计最小网络权限。需要单独处理站点写入与必要资源读取、沙箱内子进程继承限制。
3. **运行管理**：由桌面端持有预览实例，记录任务、启动进程、实际地址和状态；对不同项目开发服务器的端口参数和输出做适配与超时处理，验证实际可访问地址，不能假定都是 5173 或只靠某一种日志。端口被占用时提示或明确回退并使用真实端口；仅提供可信的本机 HTTP 地址给预览。停止、启动失败、崩溃和退出应用均需回收进程树，非正常退出及重启后要检测和恢复。构建命令、输出目录和产物检查应明确配置；不能假定所有项目都输出 `dist`。
4. **浏览器接入**：预览优先分配不冲突的端口，并修改应用页识别机制，使之基于可信页面身份而不是占用通用端口；需要同时验证用户预览和 CDP 工具。不能依赖换端口解决真实身份判断。

以上是待验证设计，并非声称现有程序已有这些能力。尤其是 Windows 隔离、网络细粒度控制和崩溃清理尚无原型；隔离不可行时，应明确调整产品安全边界与用户预期，不能把当前实验当成安全方案。

## 5. 请在 Windows 测试环境协助验证

**运行时原则：以 FTCS 桌面端实际配置的 Node 和配套 npm 为主，不要求客户预先安装全局 Node。** Windows x64 的私有运行时默认位于应用数据目录的 `node-runtime`；实际使用路径还可能由 `FTCS_NODE_PATH` 或用户配置指定。桌面端启动日志中的 `Node: 版本 · 路径（来源）` 可用于确认。当前私有运行时安装配置为 Node 24.18.0；不能仅凭该配置推断某台机器实际使用的版本。

本机实验使用的是开发机 Node/npm，不能证明桌面私有运行时可用。需要核对 npm 与 Node 是否配套、npm 脚本实际使用的 Node 路径，并覆盖无全局 Node 以及全局 Node 版本不同时的场景。站点进程使用私有运行时并不自动提供安全隔离。
