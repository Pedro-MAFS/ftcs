# TV-SITE-01 站点开发权限与本地运行技术验证

状态：**技术验证通过**。本机与 Windows 基础实验已执行；站点目录权限和命令询问采用现有机制扩展，具体实现及桌面端联动纳入后续开发验收。本文对应[交付顺序中的 TV-SITE-01](./独立站-需求拆分与交付顺序.md#tv-site-01站点开发权限与本地项目运行)，是技术验证记录，不是产品功能已交付的声明。

## 1. 验证目标与范围

验证智能体能够在受控范围内编辑一个全局站点项目，安装依赖、执行 `npm run dev` 和 `npm run build`，并让桌面端可靠地管理和打开预览。站点可以使用任意满足项目契约的纯前端 Node 项目。首期采用智能体操作权限和用户确认，不承诺对站点运行代码进行操作系统级隔离。

**站点目录约束：** 每个 FTCS 工作区在其内部约定一个固定子目录，作为该工作区唯一的全局站点项目根目录；站点源码、项目依赖、开发服务的工作目录和构建产物在此范围内管理，切换产品不切换站点。具体目录名和迁移规则在后续详设中确定。桌面端提供的 Node/npm 可以位于工作区之外，作为运行工具使用，不要求复制到站点目录。

“以站点目录作为工作目录”不等于系统隔离：项目代码、依赖、安装钩子及其子进程仍可能访问工作区其他内容或外部路径。这些能力不受 Skill 约定的强制约束，不能表述为已阻断。

验证需要回答：如何按目录控制智能体文件操作；现有硬性拒绝和 `ask` 能否按建站场景可靠处理；如何提示用户命令运行范围；如何按授权复制或重写资料；如何获取真实监听地址、识别构建产物、停止进程和处理异常；上述行为在 Windows 上是否成立。GitHub、Cloudflare 和域名链路分别在 TV-SITE-02/03 验证。

## 2. 当前实现与关键发现

- 仓库 `workspace/config/opencode/opencode.json` 默认拒绝通用编辑、命令和外部目录访问；`desktop/electron/opencode/permission-gate.ts` 对 `edit`、`bash`、`shell` 和 `external_directory` 的询问自动拒绝，任务运行期间也会自动拒绝权限询问。因此不能仅把配置改成 `ask` 就实现建站确认，必须设计受建站上下文约束的例外及桌面确认流程。`task-context.mjs` 的任务约束针对特定工具调用，不能为任意 npm 脚本提供操作系统级隔离。现有自动测试通过，不代表真实模型、真实桌面或操作系统隔离已经验证。
- 本机实验中，普通 `npm install` 的生命周期脚本以及 `npm run` 都能写入站点目录外的**临时测试目录**。因此仅设置工作目录、限制智能体工具参数或允许 `npm` 命令，不能限制脚本及其依赖的文件访问。安装带 `--ignore-scripts` 阻止了测试包的安装钩子，但之后的 `npm run` 仍可运行代码；不能据此推断所有项目依赖都兼容该选项。
- Node 权限模式在本机阻止了 Node 进程直接、经符号链接和通过 Node 子进程的测试写入；在允许启动子进程的情况下，原生 `cp` 子进程仍能写出目录。Node 权限模式因此不能单独作为运行不受信任项目的安全边界；这只是本机实验，不推断 Windows 的结果。
- `desktop/electron/browser-runtime/cdp-filter.ts` 把 `localhost:5173` 和 `127.0.0.1:5173` 判为应用自身页面，排除在相关 CDP 页面接纳和过滤逻辑之外。实际桌面预览能否显示及智能体能否操作，需要在桌面端复测，不能仅凭过滤函数推断整个预览界面的行为。

## 3. 验证代码和本机结果

[实验脚本](../experiments/tv-site-01/probe.mjs)在系统临时目录创建模拟工作区：其中 `site` 是模拟站点子目录，`outside` 是站点以外的兄弟目录和测试标记，离线运行 npm；可选使用仓库已安装的 Vite。结束时清理临时目录，只操作自己启动的预览进程。输出逐行 JSON；`pass` 为该项断言通过，`exposed` 为复现到风险，`observed` 为记录事实，`skipped` 为本环境未测，`inconclusive` 为未复现但也不能视为安全，`fail` 为实验断言失败。出现 `exposed` 不会令脚本退出失败，因为它本身是预期观察结果。

本机环境：macOS arm64、Node v24.18.0、npm 11.16.0；npm 子进程中的 Node 也是 v24.18.0。结果如下：

## 4. 已确认的首期方向与实现方案

1. **站点目录权限**：一个工作区对应一个固定的全局站点子目录。建站任务中，智能体可直接读写站点目录内文件；其他目录继续遵守已有规则。目录边界需要检查绝对路径、`..`、符号链接／junction 和不存在目标的父目录；不可只用字符串前缀判断。基于文件操作目标设计判断，并在后续功能开发时接入 OpenCode 配置与桌面端权限门；当前实现尚未按站点目录放行。
2. **命令与用户确认**：自由聊天中，站点目录内的 bash/shell 请求都走 `ask`，展示具体命令和执行目录，由用户逐次确认；拒绝或取消则不执行，站点外或无法确定目录的请求继续拒绝。自动任务运行期间，bash/shell 权限请求一律自动拒绝，不加入用户确认队列，避免任务等待；模型应收到拒绝结果，任务按实际结果继续或结束。预览、安装与构建如由桌面端提供专门入口，仍需单独设计具体授权和执行机制，不把它们视为自动放行 bash 的例外。使用桌面端配置的 Node/npm，确认界面说明项目脚本和依赖会以用户权限运行。现有权限门已有询问与自动拒绝的相似机制，后续实现时按会话、任务和站点目录接入，并验收展示及结果传递；当前规则尚未实现。
3. **资料使用规则**：生成站点的 Skill 和工作区 `AGENTS.md` 要求站点源码不直接引用站点外其他工作区目录。用户选择或授权使用资料后，复制必要文件到站点目录，或根据资料重新生成站点内容；引用站点内的副本。目录位置、导入记录和冲突处理在详设中确定。Skill/AGENTS.md 是智能体行为约定，不是强制执行边界。
4. **运行管理与预览**：记录预览实例、实际地址和状态；适配不同开发服务并检查 HTTP，处理端口占用、启动失败和停止。不能假定所有项目使用 5173 或输出 `dist`。桌面端退出及异常情况下的进程处理、构建产物配置和 CDP 5173 页面识别问题在后续功能开发时验收。
5. **明确首期边界**：无需将 Windows AppContainer、ACL 沙箱、全局网络隔离或不受信任代码的操作系统级隔离作为首期前置条件。用户批准项目脚本后，脚本及依赖可能使用用户账户已有的文件和网络权限；本轮实验已证实其可访问站点外测试目录，不能以目录限制、Node 权限或行为约定宣称其被隔离。后续如需更强保护，可另行设计验证。

以上是已确认的产品方向与实现方案，并非当前桌面端已具有这些能力。

## 5. 请在 Windows 测试环境协助验证

**运行时原则：以 FTCS 桌面端实际配置的 Node 和配套 npm 为主，不要求客户预先安装全局 Node。** Windows x64 的私有运行时默认位于应用数据目录的 `node-runtime`；实际使用路径还可能由 `FTCS_NODE_PATH` 或用户配置指定。桌面端启动日志中的 `Node: 版本 · 路径（来源）` 可用于确认。当前私有运行时安装配置为 Node 24.18.0；不能仅凭该配置推断某台机器实际使用的版本。

本机实验使用的是开发机 Node/npm，不能证明桌面私有运行时可用。需要核对 npm 与 Node 是否配套、npm 脚本实际使用的 Node 路径，并覆盖无全局 Node 以及全局 Node 版本不同时的场景。站点进程使用私有运行时并不自动提供安全隔离。
