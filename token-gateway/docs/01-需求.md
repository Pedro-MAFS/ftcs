## 1. 背景与目标

### 1.1 背景

当前桌面端要求用户自行配置大模型提供商 API Key（如 DeepSeek），存在以下问题：

- 注册与充值摩擦高，影响转化
- 产品难以形成持续收入
- 上游计费档位多（未缓存输入 / 缓存输入 / 输出等），对终端用户不友好

### 1.2 目标

建设独立的 **Token 网关**服务，作为各消费方客户端的默认模型通道（首个消费方：外贸获客桌面端）：

1. 对外提供 **OpenAI 兼容**的 Chat Completions API
2. 对外仅采用 **输入 Token / 输出 Token** 两档计费
3. 对内对接上游大模型，利用 **Token 缓存差价**获取毛利
4. 支撑预充值、用量计量、基础风控与对账

### 1.3 成功标准（MVP · 网关侧）

| 编号 | 标准 |
|------|------|
| S2 | 任意成功请求可还原：用户扣费、上游成本、缓存命中量、毛利 |
| S3 | 余额不足时新请求被拒绝；流式中断有明确结算规则；**接受**异步扣费滞后造成的透支（OQ-07） |
| S4 | 同前缀连续请求可观测到缓存命中率与毛利报表 |
| S5 | 非白名单模型、非法 Key、超限流请求均被拒绝并记日志 |

> 消费方端到端成功标准（如桌面主路径 S1）见外贸获客仓库对接文档，不在本文件验收范围内。

## 2. 范围

### 2.1 In Scope（MVP）

| 能力 | 说明 |
|------|------|
| Chat Completions 代理 | 流式 / 非流式，OpenAI 兼容 |
| 上游模型 | **仅 DeepSeek**（白名单内 DeepSeek 模型） |
| 模型白名单 | 仅放行已定价的 DeepSeek 模型 |
| 用户中心对接 | 身份来自用户中心 AS；网关为消费方应用的 **Resource Server**，不自建注册、不并列 Client |
| 网关 API Key | **一用户多 Key**；每把 Key 有唯一 `name`（客户端区分）；Chat 用 `sk-` 鉴权；余额仍在用户账户级共享 |
| 预充值余额账户 | **仅人工入账**；扣费、余额查询；金额单位 **CNY 厘** |
| 两档计费 | `prompt_tokens` × 输入价 + `completion_tokens` × 输出价 |
| 上游成本双轨记账 | 区分未缓存 / 缓存输入成本 |
| 请求账本 | 每次调用可追溯 |
| 基础风控 | RPM/TPM、日额度、余额熔断 |
| 运维方式 | **本期不建管理端**；充值/禁用/调价等通过 **直接改库**（须同步写流水） |
| 代码位置 | 本目录所属工程 `token-gateway/`（可随宿主仓库或独立演化） |
| 消费方对接 | **不在本文档展开**；见各产品对接文档（FTCS：`docs/11-官方模型通道对接.md`） |

### 2.2 Out of Scope（MVP 不做）

- 非 DeepSeek 上游（OpenAI / 其他厂商）
- 自助在线支付充值（微信/支付宝等）；卡密自动化（可后续）
- 网关自建用户注册 / 密码体系
- 将 token-gateway 注册为与桌面端并列的 OAuth Client（禁止）
- **token-gateway 管理端（Web / 管理 API / 运维脚本产品化）**——本期不做，运维直改库
- 持久化 prompts / completions 正文或排障采样
- 对外开放的通用 API 市场 / 开发者自助平台
- 多上游自动故障转移与智能路由
- 按任务包、线索包的业务套餐售卖（可后续叠加）
- 发票、税务、复杂财务系统
- 图像、Embedding、Fine-tune 等非 Chat 能力
- 企业多成员组织账户（用户中心侧已有能力亦不在本期网关范围扩展）
- 搜索服务（Tavily 等）中转计费（本期仅模型 Token）
- 后付费月结

### 2.3 非目标澄清

Token 网关 **不是** 各业务产品的业务后端（线索、画像、邮件等仍在消费方本地/业务域）。网关只负责 **模型调用的转发、计量与计费**。

身份与登录由已有 **用户中心**负责；网关维护「用户中心主体 ↔ 计费账户 ↔ **多把命名 API Key**」映射。

### 2.4 架构角色（已确认）

**token-gateway 是消费方应用的 Resource Server，不是与各桌面/客户端并列的第二个 OAuth Client。**

| 角色 | 是谁 | 说明 |
|------|------|------|
| Authorization Server (AS) | `https://user.ai-utills.com` | 唯一登录与身份源 |
| OAuth Client | 各消费方客户端（首个：`ftcs-desktop`） | 用户在 Client 登录；网关不是 Client |
| Resource Server (RS) | `token-gateway` | 校验 UC 签发的 access_token；提供计费账户与模型代理 |

约束：

1. **不**在用户中心为网关再注册一个面向终端用户的 OAuth Client。
2. 用户 **不必** 对网关单独授权/登录；信任链为：UC 登录 → 客户端持 access_token 调 RS（**携带 Key `name`**）→ RS 签发/返回该 name 下的网关 `sk-`。
3. 网关 `sk-` 是 RS 发给某客户端的 **调用凭证**（供 Agent/SDK 长期使用），**不是** 第二次 OAuth 登录；**同一用户可有多把 `sk-`，用 `name` 区分**。
4. Chat Completions 使用 `sk-` 鉴权；账户开通 / 按名获取或重置 Key 使用 UC `access_token` 鉴权。
5. 计费余额在 **用户账户级共享**（多 Key 共用一个 `balance_li`）；请求日志记录所用 `key_id` / `key_name`，便于按客户端拆分用量。

## 3. 角色与术语

### 3.1 角色

| 角色 | 描述 |
|------|------|
| 终端用户 | 通过各消费方客户端使用网关的业务人员 |
| 运营/管理员 | 通过数据库直接操作完成充值、禁用、调价等（本期无管理端） |
| 系统 | Token 网关（消费方应用的 RS） |

### 3.2 术语

| 术语 | 定义 |
|------|------|
| 消费方 / 客户端 | 持 UC 登录态、按 `name` 申请网关 Key 的应用（首个：`ftcs-desktop`） |
| 用户中心 / AS | `https://user.ai-utills.com`，OAuth 2.0 授权码 + PKCE |
| RS | `token-gateway`；校验 UC JWT、维护计费账户、代理 DeepSeek |
| 网关 API Key (`sk-`) | RS 签发的调用凭证；按 `name` 区分的多把 Key；非 OAuth access_token |
| Key 名称 (`name`) | 客户端标识字符串（如 `ftcs-desktop`）；同一用户下唯一；获取/重置时必传 |
| 输入 Token | 计入 `prompt_tokens` 的全部输入（含命中缓存部分，对外仍按输入价计） |
| 输出 Token | `completion_tokens` |
| 缓存命中率 | 命中缓存的输入 Token / 全部输入 Token |
| 厘 | 账本最小货币单位；**1 元 = 1000 厘**；库内金额均为整数，不存小数 |
| COGS | 上游真实成本（含缓存折扣后的加权成本），单位：厘 |
| 售价收入 | 按两档价向用户收取的金额，单位：厘 |

## 4. 总体架构

```
用户中心 AS (user.ai-utills.com)
    │  OAuth2（用户在消费方 Client 登录）
    │  access_token
    ▼
消费方 Client（例：ftcs-desktop）
    │
    ├── UC Bearer + name ──► Token 网关 RS
    │                        POST /v1/keys/rotate（无则创建 / 有则重置）
    │                        ◄── sk-（每次明文一次）
    └── sk- Bearer ────────► POST /v1/chat/completions
                                   │
                                   ▼
                              上游 DeepSeek
```

> 消费方 UI/配置见各产品对接文档（FTCS：`docs/11-官方模型通道对接.md`）。

### 4.1 组件职责

| 组件 | 职责 |
|------|------|
| Auth | Chat：校验 sk-；Key 签发/重置：校验 UC token + 按 name 调用 `rotate` |
| Quota | 余额预检（厘）、RPM/TPM、日额度 |
| Proxy | DeepSeek 白名单、转发上游、流式透传 |
| Meter | 解析 usage，按两档价计算应收（厘） |
| Ledger | 写请求日志、扣减余额、记录 COGS（厘） |

### 4.2 与外部系统关系

| 系统 | 关系 |
|------|------|
| 消费方客户端 | 持 UC token 调 `keys/rotate` 取 sk；Chat 使用网关 sk- |
| 用户中心 | AS / 身份源；网关不自建注册、不注册并列 Client |
| token-gateway | 本工程；本文档为其需求权威源 |
| 上游 DeepSeek | 唯一上游；网关持有上游 Key |

### 4.3 用户中心对接约定（已确认）

| 项 | 约定 |
|----|------|
| Issuer / AS | `https://user.ai-utills.com` |
| Client | 由各消费方注册（首个示例 `ftcs-desktop`）；网关不是 Client |
| Token | JWT（**HS256**），含 `tenant_id`、`user_code` 等 claim |
| 验签密钥 | RS 本地配置与 AS **相同**的 OAuth `jwk-key`（当前 UC **不支持**非对称验签主路径） |

网关侧约定：

1. 定位为消费方 RS；禁止再注册面向终端用户的 OAuth Client。
2. 不自建注册；身份键建议 `tenant_id` + `user_code`。
3. **单一 Key 接口** `POST /v1/keys/rotate`：UC token + 必传 `name`；**无则创建、有则重置**；**每次**返回明文一次（旧 sk 立即失效）。
4. **不提供** 独立的 `provision`（「已存在只回元信息、不回明文」）接口，避免丢 Key 无法自助找回。
5. Chat 用 sk-；签发/重置用 UC Bearer。
6. Scope 与各 Client 在 UC 管理端登记对齐。
7. 多命名 Key 预留多产品共用同一网关。

## 6. 接口需求

### 6.1 对客户端（公网）

| 方法 | 路径 | 说明 | 鉴权 | 优先级 |
|------|------|------|------|--------|
| `POST` | `/v1/chat/completions` | 主调用入口（仅 DeepSeek 白名单模型） | 网关 `sk-` Key | P0 |
| `POST` | `/v1/keys/rotate` | 校验 UC token；**必传 `name`**；无则创建、有则重置；返回新明文 | UC `access_token` | P0 |
| `GET` | `/v1/keys` | 列出当前用户各 Key 元信息（name/prefix/status，无明文） | UC `access_token` | P1 |
| `GET` | `/v1/models` | 白名单 DeepSeek 模型列表 | 网关 Key 或 UC token | P1 |
| `GET` | `/v1/usage/me` | 余额（厘）与今日用量（账户级；可选按 key 分解） | 网关 Key | P0 |
| `GET` | `/health` | 探活（进程存活；不因 DB 失败） | UC `access_token` | P0 |

> **不做** `POST /v1/keys/provision`（已由 `rotate` 覆盖开通场景）。

#### 6.1.1 鉴权头

```
# Chat / usage
Authorization: Bearer sk-xxxxxxxx

# 签发/重置 Key、列表、健康检查
Authorization: Bearer {user_center_access_token}
```

#### 6.1.2 `POST /v1/keys/rotate` 请求示例

```json
{
  "name": "ftcs-desktop"
}
```

**行为（单一接口）**：

| 情况 | 响应要点 |
|------|----------|
| 账户不存在 | 创建用户账户 + 创建该 `name` 的 Key，返回 `api_key` 明文一次（`action=created`） |
| 账户存在且该 `name` 无 Key | 创建该 `name` 的 Key，返回明文一次（`action=created`） |
| 该 `name` 已有 Key | **重置**：旧 sk 立即失效，返回**新**明文一次（`action=rotated`）；同用户其他 name 不受影响 |

响应除明文外可含 `name`、`prefix`、`status`、`action`（`created` \| `rotated`）。客户端须在本地安全保存明文；服务端永不二次下发同一明文。

#### 6.1.3 `GET /v1/usage/me` 响应示例

```json
{
  "user_id": "usr_xxx",
  "tenant_id": "1",
  "user_code": "u_abc",
  "balance_li": 12340,
  "currency": "CNY",
  "currency_subunit": "li",
  "li_per_yuan": 1000,
  "key": {
    "name": "ftcs-desktop",
    "prefix": "sk-ab12…"
  },
  "today": {
    "prompt_tokens": 120000,
    "completion_tokens": 8000,
    "requests": 42,
    "spent_li": 1560
  }
}
```

> UI 展示元：`yuan = balance_li / 1000`（仅展示层换算，库内与 API 主字段用厘）。  
> `today` 默认为**账户级**汇总；若请求带网关 Key，可附带当前 Key 维度用量（可选）。

### 6.2 运维操作（本期：直接改库，无管理端）

**本期不提供** 管理 HTTP 接口、管理 Web UI、产品化运维脚本。下列操作由具备数据库权限的人员在库内完成。

| 操作 | 建议做法 | 注意 |
|------|----------|------|
| 人工充值 | 事务内：`balance_li += N`，并插入 `ledger_entries`（`type=topup`，`amount_li=N`，`operator`/`note` 必填） | **禁止**只改余额不写流水 |
| 禁用/启用 | 更新 `users.status` | 禁用后 Chat 鉴权失败 |
| 重置某 name 的 Key | 更新对应 `api_keys` 行的 hash/prefix；或删旧建新 | 须与网关哈希算法一致；**按 name 定位** |
| 禁用某客户端 Key | 更新该 `api_keys.status` | 不影响同用户其他 name 的 Key |
| 调价 | 插入或更新 `price_rules`（注意 `effective_from`） | 已产生的 `request_logs` 不回改 |
| 查账 / 命中率 | 只读查询 `ledger_entries`、`request_logs`（可按 `key_name` 过滤） | 文档可附示例 SQL（非必须交付物） |

安全约定：

- 生产库写权限严格受限；操作前备份或在事务中执行
- 充值金额单位为 **厘**（整数）；例如入账 10 元 → `10000`
- 应用进程账户建议仅用业务所需权限；运维使用独立高权限账号

## 7. 计费规则（规范性）

### 7.0 货币与精度（已确认）

| 项 | 规则 |
|----|------|
| 货币 | CNY |
| 存储单位 | **厘**（整数） |
| 换算 | **1 元 = 1000 厘** |
| 禁止 | 数据库与账本字段使用浮点/小数金额 |
| 价目单位 | **厘 / 百万 Token**（整数） |
| 展示 | API 与库以厘为准；UI 可除以 1000 显示为元 |

### 7.1 计算公式

设：

- \(I\) = `prompt_tokens`
- \(O\) = `completion_tokens`
- \(I_c\) = 命中缓存的输入 Token（若未知则按 0）
- \(I_u\) = \(I - I_c\)
- \(P_{in}, P_{out}\) = 对用户输入/输出单价（**厘 / 百万 Token**）
- \(C_{in}, C_{cache}, C_{out}\) = 上游未缓存输入 / 缓存输入 / 输出单价（**厘 / 百万 Token**）

则（整数厘）：

```
revenue_li = round_half_up( (I * P_in + O * P_out) / 1_000_000 )
cogs_li    = round_half_up( (I_u * C_in + I_c * C_cache + O * C_out) / 1_000_000 )
margin_li  = revenue_li - cogs_li
```

`round_half_up`：四舍五入到整数厘。若单次计算结果为 0 但 `I+O > 0`，是否收取最小 1 厘：MVP 默认 **不强制最低 1 厘**（极小请求可为 0），上线前可用样本复核。

### 7.2 结算时机

> **OQ-07（已确认）**：Chat **请求内绝不算价、绝不扣费**；请求路径落计量日志由 **US-G0-09** 负责；算价与扣费由 **US-G0-10** 异步执行。仍做余额预检，并**接受**因此产生的额度透支。

| 场景 | 请求路径 | 异步结算 |
|------|----------|----------|
| 非流式成功且有 usage | 写 `request_logs`（用量等），`billing_status=pending`（或等价） | 算价 → 扣费 → 回填金额 → `charged` |
| 流式成功结束且有 usage | 同上 | 同上 |
| 上游失败且无 usage | 可写日志；`skipped_no_usage`（或不进结算队列） | **不扣费** |
| 流式中断且有 usage | 写日志（含已有 usage），进结算队列 | 按 usage 扣费 |
| 流式中断且无 usage | `skipped_no_usage` | **不扣费** |
| 重试 / 重复投递 | — | 以 `request_id` 幂等；禁止重复扣 |
| 缺价等不可恢复结算失败 | — | 日志 `billing_status=settle_failed`；**不扣费**；需运维补价后可人工改回 `pending` 再扫（增强项） |

### 7.3 余额预检

- 请求进入 Proxy 前检查 `balance_li > 0`（或 `>= min_balance_li`）
- **接受透支**：预检通过后、异步扣费完成前，实际消耗可超过余额；MVP **不做**金额预留 / 冻结
- 异步扣费**允许**将 `balance_li` 扣成**负数**；之后新请求被预检拒绝，直至人工充值
### 7.4 定价原则（产品约束，非代码硬编码）

- 输入价应介于「上游未缓存成本」与「预期加权平均成本」之间，按保守命中率测算（单位统一为厘/百万 Token）
- 输出价可接近成本或小幅加价（输出侧几乎无缓存差价）
- 上线前须用真实工作流样本测算 P20/P50 命中率后再定稿价目
- MVP 仅配置 DeepSeek 模型价目

- **不持久化**完整 prompts / completions 正文，**不做**排障采样（已确认）

3. Key 哈希算法与盐/pepper 须在 `token-gateway` README 写明；改库重置时按 **`api_keys.name`** 定位行。
4. 可选：仓库内附 `token-gateway/ops/*.sql` 示例（按名充值无关——充值在 users；按名禁用 Key、按日汇总），**非**上线阻塞项。
